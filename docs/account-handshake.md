# 个人账号 API 的 TCP 握手兼容

RustDesk 登录后会在连接信令服务器时发送账号令牌，因此客户端先等待服务器签名的 KeyExchange。原有 OSS hbbs 只等客户端发送业务报文，双方互等导致 `Failed to secure tcp: deadline has elapsed`。独立账号 API 无法替代这段传输握手。

实现集中在 `src/account_handshake.rs`，测试在 `src/account_handshake_tests.rs`。现有文件只增加模块声明、独立发送分支和 TCP 入口分支；不改变客户端、UDP、P2P 协调协议、hbbr 或数据库模式，也不升级服务端 hbb_common 子模块。中继请求转发前清除 API token，避免将其发给被控端。

运行 hbbs 时显式设置 `HBBS_ACCOUNT_HANDSHAKE=Y` 开启，默认关闭。握手使用 hbbs 原有签名密钥，不需要更换客户端 Key。此模块只保护信令传输，不实现 Pro 账号 ACL，也不把 API 令牌视为设备远控授权。

## 协议范围

- 连接建立后先等待至多一秒。先发数据的传统客户端和 native P2P 请求继续进入原路径，窥探操作不消费数据；等待服务器首包的客户端进入握手路径。
- 使用签名的 X25519 临时公钥和签名的版本参数，协商 KX v1，按官方客户端的 BLAKE2b 派生方法分离双向密钥，采用 libsodium XSalsa20-Poly1305。
- 服务端旧 protobuf 库不包含新增字段，因此在模块内编码 KeyExchange 的版本和签名参数扩展，不修改共享 proto。
- 仅接受 KX v1，拒绝 v0 双向复用同一 key/nonce 的旧方案。已核对官方 1.5.0 与本地 1.5.1 源码支持 v1；更旧客户端须单独验证，不能默认声称兼容。
- 最多 32 个并发握手，握手期限 5 秒，握手包最多 1 KiB，加密信令包最多 1 MiB。该服务端握手路径遇到无效协商/封装、认证失败、超长报文直接失败。
- 原版客户端的兼容握手允许收到其他首包后继续发送明文；服务端模块不能防止中间人利用这种降级。配套客户端另有小范围修复，在打洞、中继申请和账号保活发送令牌前强制完成加密 TCP 握手或使用 WSS，拒绝明文 WebSocket。需要更新客户端才能获得这项保护；仅部署 hbbs 不足以保证令牌不会明文发送。
- 首包超过一秒才到达的传统客户端可能收到握手前导包；这类异常高延迟网络不在本次实测范围。正常客户端主动首包以及 native P2P 路径另行回归。

## 合并与回滚

后续合并上游时优先保留独立模块，只检查 `lib.rs` 的声明、`Sink` 新变体、发送分支、TCP 入口分支和 token 清除这一处安全修复。若上游实现了兼容握手，应验证同样的加密协议和首包行为后移除本模块，避免叠加两套握手。

回滚可以停用 `HBBS_ACCOUNT_HANDSHAKE` 或恢复旧 hbbs 二进制，不涉及数据库迁移；但回滚后已登录客户端仍会遇到旧握手缺失问题，应先退出账号再连接。

测试：`cargo test --locked --lib account_handshake`；独立端到端探针为相邻账号项目的 `scripts/probe-hbbs.py`，使用系统 libsodium，检查传统 NAT 请求、公钥签名、版本参数、双向密钥派生和加密 NAT 请求，不发送任何账号凭据。

## 2026-10-14 部署验证

全部 14 项库测试通过（其中新模块 4 项）。Linux release 已部署到原 P2P 服务的 22116，启用上述开关，使用原有签名密钥。公网探针已通过明文 NAT 和加密 NAT；当前源码构建的 native P2P 探针双方都获得协调凭证。用户在两台已登录的 Windows 1.5.1 客户端上确认中继和 P2P 均恢复连接，并成功解锁学校电脑。此次未更换客户端程序。

原 hbbs 二进制保留为回滚文件，新进程由 `rustdesk-native-p2p-signal.service` 管理。握手属于独立模块；后续合并不需要携带测试环境、账号数据库或密钥，也无需合并整个客户端仓库。
